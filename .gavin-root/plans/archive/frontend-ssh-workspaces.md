Read `docs/superpowers/specs/2026-09-22-ssh-workspaces-design.md` and `docs/ssh-workspaces.md` first. The Rust side of ssh workspaces is in `app/src-tauri/src/remote.rs` (links, routing, the `connect_remote_workspace` command, the `remote-link-ready` / `remote-link-lost` events), `config.rs` (`Workspace.ssh: { host, daemonPath? }`) and `session.rs` (bootstrap skips ssh workspaces on the local daemon and links them after `workspaces-ready`). The frontend `Workspace` type already carries `ssh?: SshConfig` (`app/src/lib/core/workspace.ts`). Nothing in the UI can create or show an ssh workspace yet. Build that, as pure `.ts` modules with unit tests and thin Svelte templates over them, the way `orchestration.ts` and `planBoard.ts` are done.

1. **Creating an ssh workspace.** Where a workspace's root is chosen today (`WorkspaceRootControl.svelte`, `workspaceOpen.ts`, the sidebar's new-workspace flow in `sidebarMenu.ts`), add "On another machine over ssh": a host (anything `ssh <host>` accepts), the root path on the host (typed, forward slashes; there is no picker for a remote disk), and an optional daemon path. Saving sets `workspace.ssh` and `rootPath` through the ordinary workspaces save, then calls `backend.connectRemoteWorkspace(workspaceId)` (add that wrapper for `connect_remote_workspace` in `backend.ts`). Then the init-vs-bind fork: `backend.gavinRootExists(rootPath)` answers for the host when the root belongs to an ssh workspace, and rejects when the host is not linked (show that message); `initGavinRoot` is routed to the host too.
2. **Workspace settings.** The same three fields editable on the workspace settings view, with a Reconnect button (`connectRemoteWorkspace`) whose result is shown.
3. **Link state.** A store keyed by host: `connecting` until `remote-link-ready` arrives for a workspace on it, `ready` after, `lost` with the message after `remote-link-lost`. Listen for both in `layoutState.ts` next to `daemon-error`; the payload is `{ host, workspaceId?, message? }` (camelCase). A lost link is NOT `setError`: only that host's workspaces are affected, so show a banner on those workspaces naming the host and the message, with Reconnect.
4. **The remote badge.** Sidebar workspace rows and the tab strip show the host for an ssh workspace (`ssh: box`), grey while connecting, red when lost.
5. **Stale-tab protection.** `reconcileLayoutSessions` in `layoutState.ts` closes every layout tab whose session id `get_session_baselines` does not list. The baselines include every LINKED host, but a host still connecting or lost reports nothing, so `staleLayoutTabIds` (`workspace.ts`) must SKIP workspaces whose ssh host is not `ready`. Without this every remote tab is closed on startup before the link is up. Unit-test the rule.
6. **Adopting the resolved layout.** When a link resolves a workspace's sessions, Rust emits `workspaces-synced` with origin `remote:<host>` (so no window mistakes it for its own echo). Confirm `adoptWorkspaces` applies it and the remote tabs render. The terminal panes need nothing new: pushes from a link arrive on the same `pty-output` / `session-*` events.
7. **Gating the local-only surfaces.** For a workspace with `ssh` set, the Git tab, the Files tab, opening a file in the viewer, `setup_agent_integration` / the agent arm wizard, worktree setup and the delete wizard are not available yet (they run against the desktop's disk). Each shows one short notice instead of its content, through a shared pure helper (`sshLimitation(workspace)` or similar) so the wording lives once. Card Run buttons on an ssh workspace's board are disabled with the same notice until the card-runs task lands.
8. **Orchestration writes.** `set_rail_run`, `set_step_run`, `delete_tool` and `delete_group_template` accept an optional `workspaceId` now; the scheduler and the Tools tab must pass the workspace they act on (harmless for local ones), or an ssh workspace's rails are written to the local daemon.

Tests: the link-state store, `staleLayoutTabIds` skipping unlinked ssh workspaces, the gating helper, and the creation/settings reducers. Then `cd app && npm test && npm run check && npm run build`. The rendered surface is the owner's to confirm; leave a static pre-flight (grep the exact strings you rely on) in your report. Commit only the files you touched.
