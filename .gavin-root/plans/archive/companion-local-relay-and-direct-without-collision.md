CLAUDE SESSION NAME: daemon-host-check-settings-hint
## Why

Pairing a real iPhone with the release desktop over the LAN failed on 2026-10-14 with nothing telling the owner why:

- Remote access held Relay URL `ws://192.168.50.125:8445`, and that address is this Mac. 8445 is the release daemon's own **direct listener** (`crates/daemon/src/direct.rs:51`, TLS; dev is 8446). The daemon dialled itself as a Relay. Its log filled with `the Relay did not speak as a Relay does … invalid HTTP version` (the Relay dial) and `TLS did not complete: received corrupt message of type InvalidContentType` (the listener), and the phone said "Could not reach its Relay".
- The QR then carried `relays: ws://…:8445` (wrong) beside `direct: wss://…:8445` (right). Same port, two meanings, no warning in Settings, the QR or the hub.
- No Relay was running at all. A local Relay means starting `target/debug/gavin-relay` by hand with `GAVIN_RELAY_LISTEN` / `GAVIN_RELAY_TOKENS(_FILE)` / `GAVIN_RELAY_TLS_TERMINATED=1` (shell README, "To pair a real phone…"), on 8443 by default, and copying the token across.
- The direct path cannot carry the phone yet either. The shell has no native trust for the pinned cert, so every direct dial falls back to the Relay ("Companion shell: trust the direct listener's pinned certificate natively", nested under `companion-direct-listener.md`).
- The admission token is write-only in Settings: "Once saved it is not shown again. Changing the Relay URL forgets it" (`app/src/lib/core/remoteAccess.ts:440`). It can't be cleared on its own and can't be rotated.

Read first: ADR 0009 (`docs/adr/0009-a-device-can-reach-its-workstation-directly.md`), `companion-direct-listener.md`, `docs/companion-mobile.md` "Pair with a local Relay", `crates/gavin-relay/src/main.rs`, `remoteAccess.ts` (and `test-fixtures/relay-urls/cases.json`: a URL rule is asserted on both sides, add the case before changing either).

## 1. Direct + local Relay deployed side by side, never colliding

- [x] **Refuse the self-collision.** A Relay URL whose host is one of this Mac's addresses (or loopback) and whose port is a direct listener's (8445 release, 8446 dev, or `GAVIN_DIRECT_PORT`) is refused in Settings, with a line saying that port is the direct connection and naming the Relay's. Do the same check daemon-side in `remote.rs` before dialling, so a URL saved by the other build (config is shared) still says why it fails instead of looping on a protocol error.
- [x] [Desk runs the local Relay itself](./desk-runs-the-local-relay-itself.md)
  Done 2026-10-15 (decision B: the release daemon only), as protocol v73. `crates/daemon/src/desk_relay.rs` runs `gavin-relay` (a new bundle sidecar) while the option and remote access are on. It binds `0.0.0.0:<port>` with `GAVIN_RELAY_TLS_TERMINATED=1`, and its tokens come from a `0600` file. It stops when the daemon's end of its stdin closes, so it never outlives a daemon that crashed. `relay_binary` gives a dev daemon no binary, so it reports `other_build` and dials the URL and token the release one stored. `pick_port` takes the last port, else the first free one from 8443, never a direct port. The URL is `ws://<LAN address>:<port>`, written again when the address changes, with a note that phones must pair again. Turning the option off clears the URL and keeps the token. Settings has "Run a Relay on this Mac", its status line, and the URL and token fields locked while it runs. Gated by `FEATURE_MIN_VERSION.deskRelay`. `device_wire.rs` `a_device_pairs_and_connects_through_the_relay_the_desk_runs` covers it end to end.
- [x] **Explain the macOS firewall prompt** for `gavin-relay` in the UI (it silently times out both phone and daemon until allowed). Part of the desk-run Relay task above.
  `DESK_RELAY_FIREWALL_NOTE` sits under the option while it is on: answer Allow, until then the phone times out with no message, and where to change it afterwards. `docs/companion-mobile.md` says the same.
- [x] **QR: one or two?** Today one QR carries both `relays` and `direct`. Decide (decision below). If the desk offers a **Direct** QR / mode on its own, its sheet must explain what direct needs to keep working: an address that does not change (DHCP reservation / static IP on the LAN), and **a VPN such as Tailscale for when the phone is away from home**. Without one, a direct-only pairing stops working the moment the phone leaves the network or the Mac's address changes. A Relay pairing is the one that survives that.
  Decided A (one QR). `pairingSheet` in `remoteAccess.ts` reads the QR payload's `direct` and `rendezvous` lists (only those, never the secret or the token). It labels each way in "This network", "Tailnet" (100.64.0.0/10) or "Relay", in the order the phone tries them, and says what each needs. A network address needs a DHCP reservation or static IP, or the phone must pair again. Away from home needs a VPN such as Tailscale, unless the code already carries a tailnet address. With no Relay, it says so. `DevicesPanel.svelte` draws it under "Scan this…". Five tests in `remoteAccess.test.ts`.
- [x] Make the hub's per-Workstation line say WHICH path failed and with what (direct refused / Relay refused / Relay is this Mac's direct port), not only "Could not reach its Relay".

## 2. One token for direct and the local Relay

- [x] (Part of the desk-run Relay task above.) When the desk runs the Relay itself, it generates the admission token (CSPRNG, stored in the trust store like `remote_access_relay_admission`), writes it to the Relay's `GAVIN_RELAY_TOKENS_FILE` (0600), and presents the same token when it dials. Nobody copies a token by hand.
  `TrustStore::desk_admission` mints 32 bytes from `getrandom` into the existing admission row. The META `remote_access_relay_admission_by_desk` holds the token's hash, so a token typed in afterwards stops counting as the desk's with nothing to clear. The daemon dials with it, the QR carries it, and the direct listener asks for it.
- [x] [Direct listener and the admission token](./direct-listener-and-the-admission-token.md)
  Done 2026-10-15 (decision A). ADR 0009 is amended. `direct.rs` `verdict` refuses a token that is not the desk's as `admission`, checked after the rendezvous id with the constant-time `protocol::relay::admission_matches`. The core sends the token on direct dials too. That is safe now: the shell opens no pinned dial without native `trustPinned`, so nothing reaches a direct address before native pinning lands. The pin-trust card now says a pin mismatch must cancel, never fall back to default handling. `device_wire.rs` `the_direct_listener_asks_for_the_desks_admission_token` covers with the token, without it, a wrong one, and after Clear token.
- [x] (Part of the direct-listener token task above.) The QR carries the token once, used for both paths. The phone's stored record (`relayAdmission` in `hub/paired.ts`) becomes the token for both, and `readRecord` keeps reading records saved before the change.
  `begin_pairing` now puts the token in whenever the QR carries a Relay or a direct address. The phone already kept `relayAdmission` and passed it to `connect-start`, and the core now uses it for both paths. The field is unchanged, so old records read as before. A phone told `admission` by the listener says "Pair again to connect directly" (`connection/paths.ts`).
- [x] (Part of the direct-listener token task above.) Protocol: if this widens an existing request's payload, bump and add the `FEATURE_MIN_VERSION` entry plus a `featureBlockedReason` consumer on every surface that sends it (CLAUDE.md, "The compat gate is per request TYPE"). The phone must keep pairing with a desk one version behind.
  No wire change. The hello's `token` and the QR's `relayAdmission` (v52) already existed. An older desk ignores the token on direct. A newer desk refuses an older phone's empty one, and that phone falls back to the Relay.

## 3. Token clear / refresh in Settings

- [x] **Clear**: forget the token without touching the URL (today only a URL change does it).
  Already there: the Settings "Clear token" button (`clearAdmission`, sends `ADMISSION_CLEAR`; asserted by `server.rs` tests). Its note never mentioned it, so `ADMISSION_NOTE` now does.
- [x] [Refresh the token without stranding a phone](./companion-relay-token-refresh.md)
  Done 2026-10-15, in the same v73. "Refresh token" (`RefreshRelayAdmission`) works only for a token the desk minted. For someone else's token it is refused, and the line says to paste the new one. `gavin-relay` reads its tokens again on a `reload` line on stdin (`AdmissionTokens::replace`), so nothing it carries is dropped. Windows has no SIGHUP, which is why stdin carries it. A token change no longer drops the Devices a Relay carries: `remote.rs` `Dial::carries_on_under` compares the URL and rendezvous only.
- [x] (Part of the refresh task above.) Paired phones hold the old token. Decide how they get the new one: pushed over each live connection before the old one stops working (preferred, with a grace window where both are accepted), or a visible "re-pair needed" on the phone's hub. A rotated token must never strand a phone silently.
  The preferred option. The old token is accepted for 24 hours (`accepted_admissions`, `ADMISSION_GRACE`) by the Relay's file and the direct listener. Each daemon pushes `RelayAdmissionChanged` to its own live Devices when it sees the rotation (`desk_relay::refreshed`). The shell keeps the token through `Connection.onAdmission`, then `liveHub`, then `withAdmission` and `store.save`. A phone off for the whole window is refused at its next dial, and its hub says `RELAY_ADMISSION_REFUSED`: pair again. `device_wire.rs` `refreshing_the_desks_token_keeps_a_connected_device_and_hands_it_the_new_one` runs it with a 4-second window.
- [x] (Part of the refresh task above.) The token is still never displayed after saving. Show only whether one is held, when it was set, and whether the desk generated it.
  `Devices` gains `relay_admission_set_at` (the META `..._set_at`, stamped whenever the token changes) and `relay_admission_by_desk`, both defaulted. `admissionHeldLine` shows them under the token field. Gated by `FEATURE_MIN_VERSION.admissionRefresh`.

## Decisions to settle first

What the code says about each (2026-10-14):

- **QR.** The phone already dials every direct address first, each with a short timeout, and then the Relays (`companion-core` `pairing::dials`). One QR carrying both paths gives a phone at home the direct path and a phone away from home the Relay, and nobody has to choose. A direct-only pairing stops working as soon as the phone leaves the network.
- **Token on direct.** The listener already refuses any hello that does not name THIS Workstation's rendezvous id (`direct.rs` `verdict`). That id is a hash of the Workstation key the QR carries, so the gate in front of Noise already admits only people who have seen a QR. A token adds two things: it can be rotated without "Revoke all", and a revoked phone, which still knows the key, can be kept off the port. It also costs something. The core sends an EMPTY token to direct addresses on purpose, because "a LAN address a Mac has since given up could be anyone's" (`pairing.rs:84`). Sending the token there is safe only once the shell checks the pin natively, and that is still a nested task of `companion-direct-listener.md`. Phones paired before the change carry no token for direct, so they lose the direct path until they pair again.
- **Owner.** Both daemons share `devices.sqlite`, so both dial whichever Relay URL is stored, with the same token. Only the process that owns the Relay is in question.

- [x] Decision: one QR carrying both paths (today), or two QRs/modes ("Direct, same network or VPN" vs "Through a Relay")?
  Options: A) One QR carrying both, as today; the sheet under it names the paths it carries and what direct needs to keep working (Recommended) B) Two modes, each its own QR: "Direct, same network or VPN" and "Through a Relay" C) One QR, with switches under it choosing which paths it carries
  Answer (2026-10-15): One QR carrying both, as today; the sheet under it names the paths it carries and what direct needs to keep working (Recommended)
- [x] Decision: should the direct listener require the admission token (amends ADR 0009), or stay Noise-only?
  Options: A) Require it once the shell pins natively: refuse a direct hello whose token is not the desk's while the desk holds one; amend ADR 0009 B) Stay Noise-only and record why in ADR 0009: the rendezvous-id gate already admits only people who have seen a QR (Recommended) C) Require it only from phones paired after the change; the desk remembers which ones
  Answer (2026-10-15): Require it once the shell pins natively: refuse a direct hello whose token is not the desk's while the desk holds one; amend ADR 0009
- [x] Decision: which daemon owns the desk-run Relay when release and dev both run?
  Options: A) Whichever daemon takes a lock in the shared data folder first runs it; the other reads its URL and token from the trust store and takes over if the owner exits (Recommended) B) The release daemon only: a dev daemon never starts one C) The release daemon when it runs, otherwise the dev daemon, handing over when the release one starts
  Answer (2026-10-15): The release daemon only: a dev daemon never starts one
