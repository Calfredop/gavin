Add a `gavin_start_rail` tool to gavin-mcp so an orchestrating agent can arm a rail the way Start does, instead of writing `SetRailRun { state: "running" }` to the daemon socket by hand.

Why: on 2026-09-03 the Grimoria orchestrating agent found no start action among the gavin_* tools and armed five rails by writing raw `SetRailRun` rows over the socket (its conflict note `n-armed-via-socket`, and a paragraph in its project memory telling future agents to do the same). b24ed7f made that survivable — a rail armed any way now gets its own page at its first launch — but the route is still wrong on three counts. The row names no workspace, so the daemon cannot push it (`push_orchestration` needs a workspace id) and the app only adopts it on the next Orchestration-tab mount or tick. Nothing computes the first unfinished stage, so the agent guesses `current_stage_id`. And nothing refuses the two cases Start refuses, so an agent can rewind a running rail or resume a paused one without knowing it.

Read first: `startRailVerdict` and `firstUnfinishedStageId` in `app/src/lib/orchestration.ts` — the rule is: refuse a blank, unknown or ambiguous name and a PAUSED rail; no-op a RUNNING rail (Start REWINDS it) and a rail with nothing unfinished; the first unfinished stage is the first stage by position holding any step whose run row is not `done`, and card statuses play no part. Then `Request::SetRailRun` and `min_version_for` in `crates/protocol/src/lib.rs`; `set_rail_run` in `crates/daemon/src/orchestration.rs`; the `SetRailRun` arm and `push_orchestration` in `crates/daemon/src/server.rs`; the `gavin_set_orchestration` dispatch in `crates/gavin-mcp/src/main.rs` (it deserializes in the MCP so a bad argument answers the agent with serde's own message); and the gavin-orchestrate skill §2a, which today documents `Start rail` only as a rail step.

Behaviour:
- `gavin_start_rail({ rail })` takes the rail by NAME, matched case- and space-insensitively exactly as `startRailVerdict` matches it. The result text names the rail and the stage it was armed at. A refusal gives the reason in the same words the app uses. A no-op (already running; nothing unfinished) is a success that says so, never an error.
- The MCP decides: it reads `GetOrchestrationByRoot`, computes the verdict from `railRuns` and `stepRuns` alone, and only then writes. Port `startRailVerdict` minus its self-reference case rather than inventing a second rule, and leave a comment on each side naming the other so they stay in step.
- The write is a NEW daemon request `SetRailRunByRoot { root_path, rail_id, state, current_stage_id }` that does what `SetRailRun` does AND calls `push_orchestration` for the workspace the root resolves to, so an open app adopts the row at once and — with b24ed7f — the first launch lands on a page named after the rail. Keep plain `SetRailRun` untouched; the app still sends it. A root the daemon is not watching gets the same "workspace not open in gavin" every other ByRoot request gives.
- A new request TYPE is a protocol addition: bump `PROTOCOL_VERSION`, add the variant to `min_version_for`, keep gavin-mcp's compat window consistent. No `FEATURE_MIN_VERSION` entry: the app never sends this request and gavin-mcp already fails closed on skew.
- The push alone is not enough. The `orchestration-changed` handler in `initOrchestrationListeners` REPLACES the plan but KEEPS the app's own `railRuns` and `stepRuns` (the daemon's copy can lag an optimistic local write, and until now no agent authored run state), so a pushed `running` row lands in SQLite and is then dropped by a loaded workspace, which shows the rail `idle` until the next `refreshOrchestration` — the same half-adopted state Grimoria was in. Make the app adopt run state from this write without breaking that guard. The cheapest honest route is for the handler to call `refreshOrchestration` (it already skips while a save is in flight and re-checks afterwards) when the push carries a rail run state that differs from the local one; a "run state changed" marker on the push is the alternative if that read proves too chatty. Add an `orchestrationState.test.ts` case: a push carrying `running` for a rail the app holds `idle`, with no save in flight, ends with the rail running and its first step launched. Then check the workspace that is NOT the active one: the scheduler ticks only the active workspace, so the handler's own `tick` is what has to start the rail there.
- Update the gavin-orchestrate skill (§2a, or a new §2c) so an agent reaches for `gavin_start_rail` and never the socket, and add the tool to `tool_definitions` with a description that says what it refuses.

Tests. gavin-mcp stdio tests via `call_tool`: arms an idle rail at its first unfinished stage; refuses an unknown name, an ambiguous name and a paused rail, each with the app's wording; no-ops a running rail without rewinding it, and a rail with every step done; the request sent is `SetRailRunByRoot` carrying the resolved root. Daemon: `SetRailRunByRoot` writes the row and pushes `OrchestrationChanged` on the watching connection, and is refused for an unwatched root. Protocol: the new variant's `min_version_for` is the new version.

Done when: `cargo test --workspace` and `cd app && npm test && npm run check && npm run build` pass, the skill is updated, and a freshly built `gavin-mcp` driven over stdio against an isolated daemon (temp `$HOME`) arms a rail in a scratch workspace. The shared daemon needs a rebuild and restart before the running app sees the new request; that is the human's call, not this card's.

Out of scope: pause, resume and reset tools (file separately if wanted); any change to how the app itself starts a rail.
